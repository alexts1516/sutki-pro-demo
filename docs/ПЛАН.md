# План и единый источник правды

Этот файл — короткая карта проекта и список следующих решений. Если работу продолжает другой ИИ (ChatGPT или другой помощник), дайте ему ссылку на репозиторий и на этот файл. Сначала прочитайте этот файл, затем README.md и нужную техническую документацию. Новые решения и изменения сначала добавляйте сюда.

## 1. Что это за проект

Система для владельца посуточных квартир в Астане:

- бренд: **The Address · Apart Hotel**;
- объект: ЖК Highvill, пр. Кошкарбаева 10/1;
- сайт для гостей: просмотр квартир, брони, трансферы и оплата;
- админка владельца и администратора: квартиры, брони, календарь, команда, задачи и финансы;
- приложение команды: водители, мастера и специалисты по подготовке;
- сервер: база данных, вход по ролям, API, уведомления и заготовки интеграций.

Сейчас рядом существуют старое браузерное демо, демо серверной версии v2 и основа настоящего сервера.

## 2. Где что лежит

### Старое демо

Это простой прототип без сервера. Основные страницы и файлы:

- `index.html` — сайт для гостей;
- `app.html` — панель владельца/администратора;
- `cleaning.html` — приложение команды (старое имя осталось в файле);
- `task.html` — задача по одноразовой ссылке;
- `team.html` — вход для команды;
- `login.html` — вход в демо;
- `assets/` — JavaScript, CSS, бренд, переводы, данные и PWA;
- `screenshots/` — снимки экранов.

Также есть `guest.html` и `cleaner.html`: они нужны для старых ссылок и перенаправляют на новые страницы.

### Новое демо v2

Демо серверной версии без настоящего сервера находится в `v2/`:

- `v2/admin/` — админка;
- `v2/app/` — приложение команды;
- `v2/link/` — страница задачи по ссылке;
- `v2/shared/` — общие стили и компоненты;
- `v2/demo/` — браузерная имитация API и базы данных.

Открыть онлайн: <https://alexts1516.github.io/sutki-pro-demo/v2/>.
Данные v2 хранятся только в браузере посетителя.

### Сервер

Папка `server/` — основа настоящего backend на Node.js, Express и Prisma. Техническое описание находится в [`server/README_SERVER.md`](../server/README_SERVER.md).

Быстрый запуск:

```bash
cd server
npm install
npm run setup
npm run dev
```

После запуска админка открывается на `http://localhost:3000/admin/`, проверка сервера — на `http://localhost:3000/api/health`.

### Тесты

В `server/tests/` лежат тесты Node.js. Сейчас их **103** (после приёмки прохода 3). Запуск: `cd server && npm test`. Также есть проверка на PostgreSQL через `npm run test:pg` при заданном `TEST_DATABASE_URL`.

### Проход 1 — сделано (октябрь 2026)

Сделано в `server/`, демо v2 пересобрано, тесты есть (`tests/pass1.test.js`).

- **Мастер.** После «Начать работу» заявка «🔧 В работе с ЧЧ:ММ», отдельная кнопка «🏁 Завершить работу» (исправлена ошибка: раньше сразу была зелёная «выполнена»). Время начала и окончания хранится и видно. «Я приехал» — одно необязательное нажатие, без заметки и фото; «Начать работу» больше не ставит «приехал» сам. Журнал шагов свёрнут.
- **Отклонённая смета.** У мастера два действия: «✏️ Исправить смету» (новая сумма, комментарий, снова на одобрение) или «✋ Отказаться от заявки» (с причиной — заявка возвращается владельцу без исполнителя, владелец получает уведомление и выбирает другого мастера). «Нужен выезд» — маленькая ссылка.
- **Названия.** «Специалист по подготовке» (роль, карточка), коротко — «Подготовка кв. 12 — Гульнара». Внутренний ключ роли остался `cleaning`.
- **Чек-лист подготовки.** Шаблон владельца в «Настройках» (смена белья, полотенца, ванная и туалет, кухня и посуда, полы, мусор, расходники) + пункты конкретной квартиры, у пункта можно отметить «фото обязательно». Специалист: «Начать» (время) → отметки → фото → «Сообщить о проблеме» (текст + фото) → «Закончить» (время; с неотмеченными пунктами — только с комментарием). Проблема → заявка мастеру одной кнопкой. В календаре нажатие на подготовку открывает полный отчёт на месте.
- **Выплаты.** Одна модель `Payout` для всех исполнителей (подготовка — ставка квартиры / по размеру / общая; мастер — одобренная смета + одобренные доп. расходы; водитель — прежние правила комиссии). Работа владельца — без выплаты. «К оплате» создаётся сразу, владельцу приходит «Гульнара закончила подготовку кв. 12 — к оплате 5 000 ₸» с кнопками «Оплатить наличными / переводом»; напоминание через 3 часа (меняется в настройках), просроченные — красным. Экран «Выплаты» у владельца (оплатить по одной или всё человеку), у исполнителя вкладка «Выплаты». Все выплаты — в «Финансах».
- **Трансферы.** Только свои водители: внешние таксопарки скрыты (включаются только флагом `TRANSFER_EXTERNAL_DRIVERS=1`). В карточке водителя — мест, багажа, класс (седан / минивэн / микроавтобус); заказ уходит только тем, чья машина подходит по пассажирам и багажу. Владелец-водитель остаётся простым основным путём.

### Проход 3 — «операционный поток» — сделано (4 октября 2026)

Цель: модули (брони, подготовка, мастера, трансферы) связаны в одну цепочку **СОБЫТИЕ → ЗАДАЧА → ОТВЕТСТВЕННЫЙ → ВЫПОЛНЕНИЕ → ПОДТВЕРЖДЕНИЕ → СЛЕДУЮЩИЙ ЭТАП**. Новых модулей нет — переиспользованы `Booking`, `CleaningTask`, `RepairTask`, `TransferJob`, `Payout`; добавлена одна маленькая сущность `Defect` (недочёт).

#### Текущее состояние и архитектура

- `server/` — Express 5 + Prisma 6 (SQLite для разработки, PostgreSQL — `prisma/postgres/`). Демо v2 — тот же код сервера, собранный для браузера (`npm run demo:build` → `v2/`, база в браузере).
- Роли в коде (`User.role`): `owner` (владелец), `admin` (администратор), `cleaning` (специалист по подготовке), `master` (мастер), `driver` (водитель). Внешний мастер без входа — страница `/link/<токен>`. Других ролей нет и не добавлялось.
- Главный цикл квартиры: Бронь (оплачена) → подготовка (`CleaningTask`) → «Готова» (вычисляется) → заезд → проживание → выезд → подготовка → снова «Готова».
- Цикл проблемы: недочёт (`Defect`, сообщает специалист) → «Заявка мастеру» (`RepairTask`) / «Сделаю сам» / «Решено» → смета и согласование (уже было) → работа → завершение → недочёт закрывается сам → квартира снова может стать «Готова».

#### Что сделано

**P0 — связный поток**

1. **Экран «Сегодня»** (`GET /api/admin/today`, `src/services/ops.js`, первый экран админки). Не статистика, а ответ «где нужно действие». Четыре уровня: 🔴 КРИТИЧНО → 🟠 ТРЕБУЕТ ДЕЙСТВИЯ → 🔵 СЕГОДНЯ → ⚪ ИНФОРМАЦИЯ. Каждая строка: проблема → действие → срок → объект → подробности; нажатие открывает нужную карточку. Правила «Требует внимания» (нормальные процессы молчат):
   - заезд сегодня/завтра, а квартира не готова (критично, если до заезда ≤ 3 ч или есть срочный недочёт);
   - подготовка просрочена / не назначена; отчёт с пропусками ждёт проверки;
   - срочный недочёт (критично, если заезд ≤ 48 ч), обычный — в «Информации»;
   - ремонт закрывает даты заезда; заявка без мастера; работа не начата в срок;
   - смета / доп. расход ждут решения (владелец — «действие», администратор — «информация»);
   - трансфер без водителя (критично за сутки), водитель не выехал за 30 мин;
   - просьба гостя о раннем заезде → «Согласовать или отказать»;
   - неоплаченные выплаты (только владельцу); брони, ждущие оплаты на сайте, — только «Информация».
   Владельцу «Сегодня» и «Информация» свёрнуты, сверху — короткая полоса бизнеса (занято/не готово, выручка месяца, долг исполнителям).
2. **Статус «Готова» вычисляется**, кнопки нет (`apartmentState` в `ops.js`): `Гость живёт` / `Не готова — недочёт` (срочный недочёт или ремонт, закрывающий даты) / `Не готова` (подготовка до ближайшего заезда не закончена) / `Проверьте отчёт` (закончено с пропусками и комментарием — нужна «Принять отчёт») / `Готова`. Чек-лист и обязательные фото по-прежнему проверяются при «Закончить» (с пропусками — только с комментарием).
3. **Карточка квартиры** (`GET /api/admin/apartments/:id/ops`, открывается из «Сегодня», календаря, списка): что важно (почему не готова) → что сделать → гости (сейчас живёт / ближайший заезд, выезд) → подготовка (срок, кто, статус) → последние фото-отчёты → недочёты с кнопками → активные работы мастеров. Данные не дублируются — всё читается из существующих таблиц.
4. **Недочёты (#9)** — модель `Defect`: приоритет «срочно» / «можно позже», действия «Заявка мастеру» (создаёт `RepairTask`, недочёт закрывается, когда мастер завершил), «Сделаю сам», «Решено». Висит до решения. Срочный — блокирует «Готова». Видно: «Сегодня», ⚠N на плитке подготовки и в шапке квартиры в календаре (красный — есть срочный, жёлтый — только «можно позже»), карточка квартиры, карточка подготовки, а специалист на следующей подготовке видит «Известные недочёты».
5. **Защита по времени и порядку (#8)**:
   - Водитель: «Выехал» открывается за N минут до подачи (настройка «Водитель может нажать „Выехал“ за … мин», по умолчанию 120, 15–720), дальше строго по порядку Выехал → На месте → Гость в машине → Завершить. До окна поездка — «Запланировано · через N дн.» и «🔒 «Выехал» откроется 8 окт в 12:30». Администратор/владелец могут отметить шаг вручную.
   - Список водителя: по времени подачи, ближайшие сверху, группы Просрочено / Сегодня / Завтра / Позже, завершённые — отдельно; новые предложения тоже по времени (раньше падали в конец).
   - Подготовка: начать можно только в свой день; закончить — только начатую; после «Готово» ничего не меняется (кроме нового недочёта).
   - Мастер: завершить можно только после «Начать» (было в проходе 1); после завершения/отмены изменений нет.
   - Брони: отменить можно только «ждёт оплаты»/«подтверждена» и не после выезда; даты нельзя двигать у закрытых броней, дату заезда — после заезда гостя. Подготовку переносить можно только до начала.
6. **Брони по решённой модели (#10)**:
   - Сид демо: красных «заявка, не оплачено, подтвердите» нет. С сайта — оплачено картой; из Telegram/WhatsApp — «Личная ссылка» с условиями «наличные при заезде» или «залог» (это место будущей личной ссылки прохода 4). Эмма Мюллер — наличные при заезде + просьба «ранний заезд в 10:00».
   - Админка: раздел «Брони», кнопки «Подтвердить» нет, оплата показывается без красного («оплачено на сайте», «наличные при заезде», «залог»). Брони, ждущие оплаты гостем, — отдельный серый блок с кнопкой «Снять».
   - Оплата на сайте подтверждает бронь сама (`applyPaymentResult` → `confirmed`, заказ водителям уходит сразу). В демо — тестовый мгновенный провайдер `src/payments/test.js` (в продакшене отключён).
   - Ранний заезд: гость отмечает в форме → у брони «ранний заезд в 10:00 — ждёт решения» → «Согласовать» (время заезда меняется, срок подготовки сдвигается) / «Отказать».
   - Трансфер у неподтверждённой брони: кнопки «Отправить водителя сейчас» нет, API отвечает 409. Заказ водителям — только для подтверждённой брони.
7. **Экран каждой роли начинается с блока «Сейчас»**: что делать сейчас, срок, куда ехать; внизу карточки — подсказка «когда работа засчитана».

**P1, которые безопасно вошли**: «Принять отчёт» подготовки; ⚠ в календаре; полоса бизнеса владельца; подсказки шагов у мастера и водителя; ранний заезд в форме гостя.

#### Решения и почему

- `Defect` — отдельная маленькая таблица, а не JSON `problems` в подготовке: недочёт живёт дольше подготовки, у него свой статус и связь с заявкой мастеру. Старое поле `problems` оставлено для истории (не удалялось, чтобы не ломать данные).
- «Готова» не хранится в базе, а считается при каждом запросе: нельзя «забыть снять галочку», и нет второй правды.
- Правила «Требует внимания» собраны в одном месте (`todayView` в `ops.js`) — их легко менять и тестировать.
- Окно «Выехал» — настройка аккаунта, а не константа: владелец сам решает (по умолчанию 2 ч).
- Источник `link` («Личная ссылка») уже используется в данных и интерфейсе, сама ссылка — проход 4. Брони из Booking.com в демо показаны как «сайт» (по решению «другие площадки не упоминать»).

#### Сознательно НЕ сделано

- Полный поток личной ссылки и регистрация на сайте гостя — не сделаны (личная ссылка спроектирована как проход 4, см. `docs/PASS4_SPECIAL_BOOKING_SPEC.md`).
- Автоснятие неоплаченной брони через N минут (сейчас администратор снимает кнопкой «Снять»).
- Внутренний чат, CRM, ИИ, аналитика, графики, новые модули — по брифу не делались.
- Отдельный экран «Сегодня» для исполнителей не делался — у них блок «Сейчас» в своём списке.

#### Известные проблемы

- ~~Telegram-бот создаёт брони-заявки~~ — неверно (проверено 4 окт 2026: бот брони не создаёт). Реальная проблема: публичный `POST /api/public/:slug/bookings` создаёт неоплаченные `request`, которые держат даты бессрочно; закрывается в проходе 4 (спецификация, раздел 11).
- API «Подтвердить бронь» оставлен в сервере (для совместимости), в интерфейсе скрыт.
- Нет шаблона уведомления о решении по раннему заезду (`booking.early_checkin`) — гостю пока сообщают вручную.

- Сид демо зависит от текущего времени: вечером часть «сегодняшних» заездов уже «Гость живёт», и набор критичных строк другой.

Цель — доказать, что проход 3 сломан, а не что он работает. Каждая найденная ошибка воспроизведена тестом, который падал на старом коде (проверено: на коде до исправлений 5 из 6 новых тестов падают), и исправлена.

Проверенные сценарии.** Обычный заезд (бронь → подготовка → «Готова» → водитель → заезд → выезд → новая подготовка); некритичный недочёт во время подготовки; срочная проблема перед заездом (заявка мастеру → работа → закрытие → готовность сама); трансфер (окно «Выехал», порядок шагов, гонка двух водителей, завершённый заказ); ранний заезд; доступ ролей (владелец, администратор, подготовка, мастер, водитель); «Сегодня» и карточка квартиры.

**2. Как пытались сломать.** Двойные и тройные одновременные нажатия («Подтвердить», «Закончить», «Сообщить о проблеме», «Заявка мастеру», «Завершить работу»); повтор запроса после обновления страницы; неверный порядок («готово» без «Начать», «Завершить» без «Начать», шаги водителя вразнобой); действия над закрытым («Решено» повторно, заявка по решённому недочёту, «Начать» после закрытия заявки, переназначение завершённой поездки); закрытие недочёта раньше мастера; ранний заезд раньше выезда предыдущего гостя; повторное согласование; смена исполнителя посреди работы; прямые вызовы API от исполнителей к экранам админки; утечки (телефон гостя, деньги).

**3. Найденные реальные проблемы.**
1. Двойное подтверждение брони (двойной клик или повтор уведомления об оплате) создавало **две подготовки** и пыталось создать второй заказ водителям.
2. «Закончить подготовку» не было защищено от одновременного двойного нажатия (выплату спасала уникальность записи, но второе уведомление и вторая запись статуса были возможны). Найдено чтением кода, гонку тестом не воспроизвели — защищено профилактически.
3. Через API подготовку можно было сразу отметить «готово», перепрыгнув «Начать» (`/status {status:'done'}`).
4. Повторная отправка «Сообщить о проблеме» создавала **копии недочёта** (3 одинаковых).
5. Двойное «Заявка мастеру» по одному недочёту могло создать **две заявки**.
6. Недочёт с живой заявкой мастеру можно было закрыть «Решено» — квартира становилась «Готова», хотя мастер ещё не работал.
7. Двойное «Завершить работу» у мастера писало две записи «завершено» в журнал (и два уведомления); вообще смены статуса заявки не были защищены от гонки.
8. Ранний заезд можно было согласовать на время **раньше выезда предыдущего гостя** (например, 10:00 при выезде в 12:00).
9. Смена исполнителя у подготовки «В пути» оставляла задачу «в пути» без человека (тупик).
10. В приложении команды при повторном нажатии шага поездки (409) карточка не обновлялась — человек видел устаревшее состояние (найдено чтением кода интерфейса).

**4. Что исправлено.**
- Подтверждение брони — условная запись (`updateMany where status='request'`): повтор возвращает уже подтверждённую бронь, подготовка и заказ создаются один раз (`services/bookings.js`).
- «Закончить подготовку» — условная запись из `progress`; «готово» только после «Начать» (`services/cleaning.js`).
- Недочёты: повтор того же текста по той же квартире за 10 минут возвращает существующий (срочность можно только повысить, фото добавляются); «Заявка мастеру» и создание недочёта идут строго по очереди; «Решено» при активной заявке — 409 с подсказкой «отмените заявку, если мастер не нужен»; в админке кнопка «Решено» скрыта, пока есть заявка (`services/defects.js`, `admin.js`).
- Заявки мастеру: каждая смена статуса — условная запись; одновременное второе действие получает 409 «Заявку уже изменили — обновите карточку» (`services/workRequests.js`).
- Ранний заезд: если в тот же день выезжает предыдущий гость, согласовать можно не раньше его выезда + 2 ч на подготовку; иначе 409 с подсказкой, какое время предложить (`routes/admin/ops.js`, константа `PREP_MIN = 120`).
- Смена исполнителя у «В пути» возвращает задачу в «Назначена» (`routes/admin/operations.js`).
- Приложение команды: на 409 при шаге поездки — причина + свежая карточка (`shared/views.js`).

### Брони и оплата (решено)

- Обычный гость бронирует **только с оплатой на нашем сайте**. Брони без оплаты нет.
- Особый случай: гость пишет владельцу в Telegram. Владелец или администратор одобряет и создаёт **личную ссылку с ограниченным сроком**: даты и условия (наличные при заезде или залог). Гость по ссылке вводит имя и телефон, соглашается с условиями — бронь подтверждается. **Паспорт и билет по умолчанию не нужны** (решение владельца от 4 окт 2026): это только необязательное дополнительное подтверждение для исключительной брони, его запрашивает владелец/админ для конкретной ссылки; в проходе 4 документы присылаются вне системы, в системе — отметка «Подтверждение получено». Миграционный учёт иностранцев / eQonaq — отдельный будущий этап, привязанный к заселению.
- Ответственный за такие обращения задаётся в настройках: по умолчанию владелец, можно передать администратору. Напоминания через 1 ч и 6 ч, до истечения 24 ч — передача владельцу. *(Уточнено спецификацией прохода 4: эти цифры — не окончательные; в проходе 4 — пункты «Сегодня» за 3 ч и 1 ч до конца срока, Telegram-напоминания — отдельная задача после прохода 4.)*
- Если позже паспорта будут загружаться в систему — их видят только владелец и администратор.
